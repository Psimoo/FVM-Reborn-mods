# 子弹与敌人对象池设计与实施方案

## 目标

对象池的目标是减少高频 `instance_create`、初始化和 `instance_destroy` 造成的 CPU 峰值。推荐先池化普通子弹和短生命周期特效，再处理普通敌人。Boss 和带复杂附属对象的敌人放到后续阶段。

对象池不会自动减少碰撞检测。子弹仍然需要通过粗筛、行索引或网格索引降低碰撞成本。

## 当前实现的基础

项目已有 [obj_pool.gml](D:/gameProject/FVM-Reborn-mod/scripts/obj_pool/obj_pool.gml)，提供：

- `obj_pool_prealloc`：预创建实例；
- `obj_pool_get`：从池中取出实例；
- `obj_pool_release`：将实例放回池中；
- `obj_pool_clear`：清空对象池。

当前实现仍需补强：许多子弹直接调用 `instance_destroy()`；多数对象没有统一的池内停用检查；`event_user(14)` 不是所有对象都实现了完整重置；敌人的 Destroy 事件包含注销和掉落逻辑，不能直接照搬到池化回收流程。

## 对象状态

每个池化对象应明确处于以下状态之一：

| 状态 | `active` | `pooled` | 是否 Step | 是否 Draw |
|---|---:|---:|---:|---:|
| 池内 | 0 | 1 | 否 | 否 |
| 场内 | 1 | 0 | 是 | 是 |
| 待回收 | 0 | 1 | 否 | 否 |

建议所有池化对象都有：

```gml
active = false;
pooled = true;
pool_generation = 0;
```

池内对象不能只设置 `visible = false`。隐藏并不等于停止 Step、碰撞事件和计时器。

## 子弹池流程

### 预创建

战斗开始时按照预计峰值预创建，而不是一次性创建所有可能的子弹：

```gml
obj_pool_prealloc(obj_coffeecup_bullet, 120);
obj_pool_prealloc(obj_war_god_bullet, 80);
```

预创建对象必须处于非活动状态：

```gml
active = false;
pooled = true;
visible = false;
x = -10000;
y = -10000;
```

### 发射

发射时从池中取出对象，并完整写入本次发射参数：

```gml
var bullet = obj_pool_get(obj_coffeecup_bullet, start_x, start_y, depth);
with (bullet) {
    active = true;
    pooled = false;
    visible = true;
    damage = source_damage;
    damage_type = source_damage_type;
    move_speed = source_speed;
    row = source_row;
    life_timer = 0;
    image_index = 0;
    image_alpha = 1;
    image_angle = source_angle;
    pool_generation += 1;
}
```

不能只设置 x、y 和 visible。伤害、行号、目标类型、穿透记录、动画帧和生命周期都必须重置。

### Step 保护

所有池化子弹的 Step 开头都应有：

```gml
if (!active || pooled) exit;
```

如果使用 `instance_deactivate_object` 和 `instance_activate_object`，可以让池内实例完全停止 Step、Draw 和碰撞，但必须确保对象池管理器本身不会被停用。

### 回收

命中、出界、碰撞障碍物和生命周期结束都必须走统一回收接口：

```gml
pool_release_bullet(id, "hit");
exit;
```

推荐统一清理以下字段：

```gml
active = false;
pooled = true;
visible = false;
x = -10000;
y = -10000;
speed = 0;
hspeed = 0;
vspeed = 0;
image_index = 0;
image_alpha = 1;
image_angle = 0;
life_timer = 0;
damage = 0;
target = noone;
hitted_enemy = [];
```

具体字段必须按照每个子弹的 Create 事件补齐，不能假设所有子弹字段完全一致。

## 敌人池流程

敌人对象池比子弹池复杂。当前敌人生命周期涉及：

- `global.enemy_by_type` 类型注册；
- 死亡动画和透明度；
- 掉落金币；
- 冰冻、减速、眩晕和驱赶状态；
- 目标植物引用；
- 护盾、头盔和特殊死亡标记。

因此“死亡”和“回收到池”必须分开：

1. 执行一次死亡结算、掉落和死亡音效；
2. 播放死亡动画或隐藏对象；
3. 清除类型索引和全部状态；
4. 将对象放回池中。

重新激活敌人时至少重置：

```gml
active = true;
visible = true;
state = ENEMY_STATE.NORMAL;
hp = maxhp;
target_plant = noone;
ice_timer = 0;
frozen_timer = 0;
stun_timer = 0;
scare_timer = 0;
flash_value = 0;
is_frozen = false;
is_slowdown = false;
is_stun = false;
is_scare = false;
shield_hp = shield_max_hp;
helmet_hp = helmet_max_hp;
image_alpha = 1;
image_index = 0;
timer = 0;
attack_timer = 0;
```

重新激活后还必须重新加入 `global.enemy_by_type[target_type]`。否则子弹会无法命中，或者保留已经死亡敌人的旧 ID。

## Destroy 事件风险

`objects/obj_enemy_parent/Destroy_0.gml` 中包含类型注销和随机掉落。池化回收不能直接调用普通 `instance_destroy()`，否则可能造成重复掉落、重复音效或战斗结算异常。

可以增加清理标志：

```gml
pool_cleanup = true;
instance_destroy();
```

Destroy 事件区分两种路径：

```gml
if (pool_cleanup) {
    // 只释放引用和索引，不执行死亡奖励
    exit;
}

// 正常死亡掉落和结算
```

更稳妥的方案是：战斗结束时先清理池内实例，再统一销毁，不让清理过程触发死亡奖励。

## 池化与碰撞优化必须分开

对象池只解决创建和销毁，不解决 `precise_bbox_collision` 的计算量。建议同时做三层碰撞优化：

1. 先判断敌人类型；
2. 再判断行号、x 轴距离和简单矩形；
3. 最后才调用 `precise_bbox_collision`。

如果碰撞每 2 帧执行一次，必须保存上一帧位置并做连续碰撞检测，否则高速子弹会穿过敌人：

```gml
previous_x = x;
x += move_speed;
// 检查 previous_x 到 x 的运动线段
```

移动、绘制和碰撞降频不能混为一谈。建议保持移动每帧更新，只对碰撞候选检查降频。

## 容量策略

建议使用“预创建 + 动态扩容”：

```text
初始容量 = 预计同时活跃数量
池为空时 = 动态创建一个实例
记录峰值 = 下一局按峰值增加预创建数量
```

不建议按照理论最大值预创建所有对象，因为会增加启动时间和内存占用。池为空时允许动态创建，避免发射失败或敌人波次缺失。

## 推荐接口

建议逐步统一到以下接口：

```gml
pool_acquire_bullet(_obj, _data);
pool_release_bullet(_inst, _reason);
pool_acquire_enemy(_obj, _data);
pool_release_enemy(_inst, _reason);
pool_reset_instance(_inst);
```

所有发射、命中、死亡和出界路径都通过这些接口处理，避免不同对象各自实现不完整的回收逻辑。

## 实施顺序

1. 选择一种普通子弹接入对象池；
2. 验证发射、碰撞、命中、出界和回收；
3. 接入爆炸、火焰和受击特效；
4. 确认池内对象不执行 Step、Draw 和碰撞；
5. 记录实例创建/销毁次数和 FPS；
6. 选择一种普通敌人进行池化；
7. 验证死亡、掉落、类型索引和状态重置；
8. 扩展到其他普通敌人；
9. 暂时保留 Boss 和复杂附属对象的普通生命周期。

## 验收指标

必须在同一关卡、同一波次、同一卡组下比较：

- 平均 FPS；
- 1% 最低 FPS；
- 单帧最长耗时；
- 每秒实例创建次数；
- 每秒实例销毁次数；
- 同时活跃的子弹和特效数量；
- 命中数量和 DPS；
- 敌人掉落数量；
- 高速子弹穿透数量；
- 战斗结束后的池内引用数量。

如果对象池接入后瞬时卡顿明显减少，说明实例创建销毁是重要热点。如果持续低帧仍存在，则继续优化精确碰撞、敌人按行索引和全局动态对象扫描。

## 结论

“提前准备子弹，发射时加入场内，结束后回收到池”是正确方向。推荐先做子弹和特效，再做普通敌人。实现重点是统一生命周期、完整重置状态、停止池内 Step、正确维护敌人索引，以及避免 Destroy 事件重复执行掉落逻辑。
