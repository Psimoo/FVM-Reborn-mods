# 子弹碰撞与工匠神性能优化记录

> 项目：FVM Reborn mods（GameMaker Studio 2）
> 时间：2026-10-03 ~ 10-04
> 场景参数：1920×1080，格子 107×116，`grid_cols` × `grid_rows`，子弹/敌人数量可达数百

---

## 0. 先搞清楚"贵"在哪里

Profiler 最初的数据（海星子弹）：

| 函数 | 调用次数 | 时间(毫秒) | 步 % |
|---|---|---|---|
| `obj_coalstarfish_bullet_Step_0` | 3,686,760 | 95,058 | 55.42% |

一颗子弹的 Step 占了整帧的一半。拆开看，昂贵的是这个循环：

```gml
for (每一只可命中类型的老鼠) {
    if (!instance_exists(_e)) continue;         // ← 每只怪都要调一次，约 100ns
    if (_e.hp <= 0) continue;
    if (row 过滤) continue;
    if (precise_bbox_collision(id, _e)) { ... }  // ← 每次都要重算子弹的旋转包围盒
}
```

**结论：这个游戏里真正的开销是"每帧每颗子弹遍历敌人列表"，而不是算法复杂度。**
后面的所有优化都是围绕这一句展开的。

## 1. 对象池（子弹 / 特效 / 部分敌人）

**做法**

- 新增 `obj_pool_holder`：无事件、无贴图、不可见的空壳对象；
- 用 `instance_change` 复用实例：
  - 取出：`instance_change(真实对象, true)` → 跑一遍 Create（重置状态）
  - 回收：`instance_change(obj_pool_holder, true)` → 跑一遍 Destroy（执行死亡逻辑）
- 用全局宏劫持创建/销毁入口（`scripts/src_hook_function`）：

```gml
#macro instance_create_depth_origfunc instance_create_depth
#macro instance_create_depth          instance_create_depth_define
#macro instance_destroy_origfunc instance_destroy
#macro instance_destroy          obj_pool_instance_destroy
```

- 池化范围：对象名含 `bullet` / `explode` / `ash_death` / `death_effect` 的自动池化；
  敌人用**显式白名单**（平民/球迷/铁锅/巨人/熊猫及全部衍生形态）。

**按卡组预热**（`scripts/obj_pool_deck`）

- `_gen_deck_map.py` 扫描每个植物对象引用到的子弹/特效对象，生成 256 条映射；
- 进关（`obj_battle` 的 Room Start）只预热**当前卡组**带进来的卡；
- 不是一次性生成，而是**排队 + 每帧生成一小批**（`obj_pool_prewarm_tick`），避免进关瞬间卡顿。

**必须记住的一条结论**

> 关掉对象池后，"刷怪瞬间卡"**依然存在**。
> 所以池化解决的是"频繁创建/销毁"的抖动，**它不是刷怪卡顿的元凶**。

## 2. 子弹碰撞的四次迭代（含两次失败）

### 2.1 内联包围盒 —— 有效，1.83 倍

原来对场上**每一只**敌人都调用一次 `precise_bbox_collision(id, _e)`，
而那个函数每次都重新计算**子弹自己的旋转包围盒**（4 个角旋转 + min/max）。

改成：

```gml
if (precise_bbox_prepare(id)) {          // 每帧/每颗子弹只算一次，写入 global._pbc_l/r/t/b
    var _al = global._pbc_l; ...
    for (每一只敌人) {
        if (_e.bbox_right < _al || _e.bbox_left > _ar || ...) continue;   // 内联比较，不调函数
    }
}
```

| | 时间(毫秒) |
|---|---|
| 优化前 | 95,058 |
| 优化后 | **51,916** |

### 2.2 判定降频 —— 有效

慢速子弹不需要每帧判定：

```gml
hit_tick++;
if (hit_tick >= global.bullet_hit_interval) {   // 默认 2 帧；海星单独用 3 帧
    hit_tick = 0;
    ...碰撞扫描...
}
```

**安全性论证**：子弹一帧位移 ≤8px，2~3 帧 ≤24px；敌人最快迎面 2.25px/帧；
合计相对位移 ≤31px，而敌人 bbox 宽 100~180px —— **不可能穿过敌人**。

### 2.3 空间索引（网格 / 分桶）—— **失败两次**

| 尝试 | 每次调用耗时 |
|---|---|
| 内联全表遍历（2.1） | **13.2 µs** |
| 5×5 网格 + 每格缓存 | 更卡 |
| 3×3 网格 + 同格共享缓存 | 14.4 µs（**反而慢 9%**） |

**为什么失败**

- 剪枝省下的"遍历量" < 索引自身的固定开销；
- 更根本的是：**`instance_exists(_e)` 是每只怪的固定成本，分桶一秒钟都省不掉**；
- 剪枝只减少"要看几只"，不减少"每只多贵"。

> 结论：**这个游戏的敌人列表不够长，通用空间索引不划算。**

### 2.4 全域 x 范围剪枝 —— 有效，但脆弱

每帧算一次全体敌人的 `min(bbox_left)` / `max(bbox_right)`，子弹在扫描前做一次 O(1) 判断：

```gml
if (global.enemy_min_left > 子弹右边 + 余量) → 整段扫描跳过
```

**问题：离群怪会让它失效。**
`空降爆破鼠` 会瞬移到第 2~6 列、`伞兵鼠` 从屏幕上方降落 ——
只要有一只怪落在别处，`enemy_min_left` 就被拉到很左，所有子弹的剪枝全部失效。

## 3. SAP（Sweep and Prune，扫描线剪枝）

### 3.1 原理（来自 `E:\Download\index.html`）

```js
aabbs.sort((a, b) => a.left - b.left);              // ① 按左边界排序
while (queue[0]?.right < aabbA.left) queue.shift()  // ② 活动队列丢掉"右边界够不着"的
for (...) if (aabbA.intersects(aabbB)) ...          // ③ 只和剩下的比
```

**最关键的性质**

> SAP 只产出"**可能相交的候选的父集**"，
> 真正的判定仍然是原来那句 `precise_bbox_collision(id, _e)`。
> **多给的候选会被它否掉，少给一个都不行 —— 所以碰撞体积一个像素都不会变。**

这一点正是 2.3 里格桶做不到的：格桶是**上一帧**建的索引，
大怪的 bbox 随动画换帧变化后，索引可能已经**漏掉**它，等于把体积改小了。

### 3.2 在本工程里的落地

**每帧建索引**（`objects/obj_battle/Step_2.gml`，并入原有的那遍 O(N) 遍历）

```gml
1. 遍历所有类型表，收集存活敌人 id（顺便清死 id、算每列敌人数）
2. 快照：_ebt_sl[i] = bbox_left，_ebt_sr[i] = bbox_right
   ← 必须快照成"数值"，因为查询发生在下一帧，
     直接读实例 bbox 遇到已销毁实例会直接报错
3. 希尔排序（按左边界，同步搬移 id / 右边界）
4. 前缀最大值：_ebt_pm[i] = max(bbox_right[0..i])
5. 发布 global.enemy_sx / enemy_sx_l / enemy_sx_pmax / enemy_sx_gen
```

> 不用 `array_sort`：它**原地排序，返回值不可用**（赋值给变量会让它变成非数组）。

**子弹侧查询**（`scripts/precise_bbox_collision` → `bullet_sap_type_list`）

```gml
_ql = 子弹左边 - 余量;  _qr = 子弹右边 + 余量;

// 二分：最后一个"左边界 <= _qr"的下标
while (_lo <= _hi) { _mid = floor((_lo + _hi) / 2); ... }

// 从后往前扫，"前缀最大右边界都够不着"就整段停
for (var i = _last; i >= 0; i--) {
    if (_pm[i] < _ql) break;                 // ← SAP 的活动队列剪枝
    if (_e.bbox_right < _ql) continue;
    ...x/y 实时判定 + 类型过滤...
}
```

**正确性**

- `i > _last` 的怪：左边界 > 子弹右边 → x 方向不可能相交；
- `_pm[i] < _ql` 的下标 0..i：右边界都 < 子弹左边 → 同样不可能相交。
- 两边都排除干净 ⇒ **不漏**。

**余量 128**：覆盖"索引是上一帧建的"（一帧位移 + 动画 bbox 变化）。
余量只会让候选**多**，不会少。

**每帧缓存**：`_sap_gen` 记帧代号，同一颗子弹同一帧只建一次候选列表，
其余类型调用只做廉价类型过滤（工匠神子弹有 7 种类型！）。

**零分配**（这条踩坑最狠）：

```gml
var _all = [];        // ✗ 每次调用都新建 → 7 类型 = 7 次分配/判定
var _out = [];
```

改成**每颗子弹复用缓冲区**：

```gml
if (!variable_instance_exists(_inst, "_sap_all")) _inst._sap_all = [];
var _all = _inst._sap_all;
array_resize(_all, 0);      // 原地复用，不新建
```

（GML 数组是引用语义 —— 工程里敌人注册就是靠 `array_push(global.enemy_by_type[$ key], id)` 生效的。）

## 4. 固定弹道的特化（工匠神竖向子弹）

竖向子弹的 `x` 是**锁死的**，因此：

1. **删掉每帧重算 x**：创建位置本来就是列中心，公式一模一样 → 纯浪费；
2. **上下边界缓存到 Create**：只依赖网格全局，整关不变；
3. **剪枝改成"列存在性"判断**：x 固定 ⇒ 只可能在 `col-1 .. col+1` 三列里碰到人。

```gml
global.enemy_col_n[列]：该列 bbox 覆盖到的敌人数量（每帧随敌人遍历 +1）
```

```gml
for (var _cc = _cc0; _cc <= _cc1; _cc++) {
    if (global.enemy_col_n[_cc] > 0) { _has_col = true; break; }
}
```

- **精确**：计数为 0 ⇒ 该列没有任何 bbox 覆盖 ⇒ 锁在这一列的子弹不可能命中；
- **±1 列**是为了盖住"计数是上一帧建的"（位移 ≤3px、bbox 变化 ≤30px，都远小于一格 107px）。

## 5. 工匠神本体：去掉索敌

原来是**每帧 × 每张卡 × 全体敌人**的扫描：

```gml
var has_enemy = false;
with (obj_enemy_parent) { if (...) { has_enemy = true; break; } }
if (has_enemy) { attack_timer++; ... } else { attack_timer = 0; ... }
```

改为**放下即持续攻击**：直接 `attack_timer++`，开火节奏 / 动画时序 / `event_user(1)` 全部不变。

（场上约 47 张工匠神，这一块占 5.17% 的帧时间，删掉后只剩计时器。）

## 7. 教训

1. **先量再改**。三次空间索引尝试里有两次是负收益，靠 Profiler 才发现。
2. **在 GML 里，函数调用和数组分配常常比算法复杂度更贵**：
   - `instance_exists` / `variable_instance_exists` / `variable_global_exists` 每次 ~0.2-0.5µs；
   - 一次 `var x = []` 的分配，乘上"每帧几百颗子弹 × 7 种类型"就变成主要开销。
3. **索引可以"多给"，不能"少给"**。SAP 之所以安全，是因为它只做粗筛，
   真正的判定永远留在原地 —— 这才保证了碰撞体积不变。
4. **凡是"上一帧建的索引"，都要留余量**，否则大怪的动画 bbox 变化会让它漏人。
5. **别用"全局极值"做剪枝**：一只离群怪（空降鼠）就能让全场的剪枝失效。
